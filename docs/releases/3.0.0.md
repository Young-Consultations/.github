# AI-SDLC 3.0.0 corrective release candidate

**Status:** unpublished candidate.

Published `ai-sdlc-v2.4.5` remains the active control plane until this
candidate is reviewed, merged, tagged, separately attested, preflighted, and
adopted by the source consumer.

## Why this is a MAJOR release

REAL issue #156 exposed control-plane defect #83: the deployed result credential
could not authenticate its own durable receiver journal evidence on equivalent
redelivery. The selected repair uses the dedicated GitHub App
`ai-sdlc-result-writer` and changes the reusable result-receiver secret
interface from `CODEX_RESULT_TOKEN` to `RESULT_WRITER_PRIVATE_KEY`.

The approved release policy classifies removing or renaming a required workflow
secret, or changing its meaning, as MAJOR. Organization issue #85 therefore
reclassified the repair from the unused 2.4.6 target candidate to 3.0.0.

The payload schemas do not change. `ai-sdlc-contract/v2` remains the canonical
payload namespace.

## Result-writer identity and credential boundary

The result writer is GitHub App `ai-sdlc-result-writer`, App ID `5100679`,
installed only on `Young-Consultations/portfolio-tasks`.

Before Codex, the enabled consulting target:

1. runs its authoritative admission/schema gate;
2. mints a short-lived App installation token scoped only to
   `portfolio-tasks` with Issues write and Contents write;
3. verifies the returned App slug;
4. runs the organization-owned result credential capability preflight; and
5. exposes the OpenAI credential only after those checks succeed.

After target execution, the reusable result receiver receives only
`RESULT_WRITER_PRIVATE_KEY`, mints a **fresh** installation token, verifies the
same App slug, and passes only that short-lived token into the immutable receiver
action. The private key and App token do not enter the Codex adapter.

The immutable result-author policy trusts
`ai-sdlc-result-writer[bot]`. Admission remains owned by the separate
`mightyjoe909` identity. Role overlap remains prohibited.

The source projector listens only to repository-dispatch event
`ai-sdlc-execution-result-v2`. The credential preflight event
`ai-sdlc-result-credential-preflight-v1` therefore has no source business
logic attached to it.

## Publication and deployed gates

1. Merge the reviewed candidate after candidate readiness, exact target
   compatibility, SIM, complete tests, and protected checks pass.
2. Re-run those checks on the exact merge commit and confirm
   `ai-sdlc-v3.0.0` does not yet exist.
3. Create lightweight `ai-sdlc-v3.0.0` at that exact merge commit. Do not move,
   delete, or recreate a published tag.
4. Open a separate publication-attestation PR recording the resolved tag commit,
   set `tag_published: true`, regenerate `release/current-runtime.json`, and
   pass `validate_release.py --require-publishable`, remote target verification,
   complete tests, and review.
5. After attestation merges, run deployed Runtime Preflight and immutable REAL
   preflight.
6. Update portfolio-tasks to consume `ai-sdlc-v3.0.0` through its own reviewed
   PR.
7. Run a fresh controlled REAL delivery and same-delivery redelivery.
8. Close #83 / consulting DEF-0064 only after the REAL evidence proves one
   managed draft, no second Codex execution, one trusted receiver effect, and
   one source projection.

Candidate validation, tag creation, attestation, and preflight are evidence
gates. None alone is REAL acceptance.

## Rollback boundary

The existing `previous_known_good` metadata remains subject to organization
issue #82. It is not automatic authority to resume cost-bearing execution.
Published 2.4.4 is known unsafe in the publication path, and 2.4.5 has the
unresolved result-redelivery defect. If rollback is required before a separately
reviewed safe release is identified, keep REAL implementation disabled rather
than inferring safety from the manifest field.
